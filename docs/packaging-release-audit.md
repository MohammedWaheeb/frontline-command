## Findings and corrections

| Concrete finding | Correction / verification |
| --- | --- |
| Every prior pack used id/version `2.0.0`, while the installer reuses that pair. Base v24 and its 34-asset union have different bytes under the same identity. | The read-only comparison preserves this failure. Future versions are `content-v1-<SHA256>` over canonical descriptors, with the index's generated base-version self-reference normalized to avoid a circular hash. Stable ID remains `2.0.0`; the staged index receives the new version and its final bytes are hashed into the manifest. Nine packaging tests pass, including repeated-build stability, changed bytes/size/addition/path and index propagation. |
| Offline fallback searched every retired cache, allowing a removed path to be resurrected from an older generation of the same pack. Install timestamps could tie within one millisecond. | Fallback considers one newest completed generation per pack ID. Activation rereads complete generations at commit/rollback under a short per-pack Web Lock; downloads hold no lock. Explicit reuse of an older completed pack activates rollback without download, while an initially canceled request cannot activate it. Tests cover old offline content, interrupted staging, corrupt new bytes, successful new index/WASM/root navigation, removed-path refusal, unchanged reuse, retained old caches, a held download completing after another install, and deterministic legacy timestamp ties. No automatic retired-cache deletion policy was invented. |
| Pack assembly trusted a successful Vite build, checking only `index.html`; it lacked exact required-runtime/path checks. | A reusable validator checks every descriptor's SHA/length, mandatory worker/WASM/Go shim/service worker/index files, HTML references, index identity, symlink/case/path portability and unlisted files. It runs before copying and again on the stage. Source maps may remain local but are intentionally outside the offline pack. |
| Inherited Go cross-build settings could emit a non-native binary under a native package name. Runtime inspector naming also omitted `.exe` on Windows. | Native target/CPU and no-CGO build environment are explicit; native header verification must match. Windows uses `runtime-native.exe`. This is source/helper validation, not an executed Windows or Linux build. |
| Direct `execFile`/`spawn` of Windows `npm.cmd` is unsupported without a shell. | The command runner locates `npm-cli.js` beside the installed Node/npm and executes it with Node; it does not introduce shell interpolation. The final launcher uses an explicit current-directory executable and checks directory change. Real Windows execution remains open. [Node documentation](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows) documents the original restriction. |
| Package metadata came from mutable `client/public/runtime`, and host/client/content could be built across a source change. The Go runtime license was omitted. | Metadata now comes from the copied stage. A fingerprint of 210 current production Go/protocol/content inputs must be identical before/after assembly; target metadata and pack receipt are recorded. Go's LICENSE accompanies `wasm_exec.js` and native runtime notices. No broad Go or client rebuild was performed. |

Without Web Locks, activation is serialized only within one JavaScript context. Cross-tab atomic activation is **not** promised in that fallback: equal timestamps have the same deterministic cache-name ordering in the installer and service worker, and the reader still selects one whole generation. Genuine multi-tab Web Lock/cancellation acceptance remains a browser gate. The new worker is network-first as before; only its offline fallback generation selection changed, and authenticated/private API requests remain excluded. A stale worker may keep the old fallback until its normal update/activation, so that upgrade boundary must be checked in a real browser.

`writeBasePack` validates referenced content, scenery, effects and audio before writing. These checks plus temporary JSON renames preserve the prior index/manifest on validation failure. A filesystem crash between two renames is not a two-file transaction: the build directory must stay unpublished until the full package is complete. Frozen overlays must use a newly locked helper generation to receive this fix; their old manifests must never be rewritten or relabeled.
