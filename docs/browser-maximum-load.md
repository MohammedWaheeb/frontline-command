# Browser maximum-load verification

The fixture uses the same pure Go engine and save format as the game. It begins
with the legal four-player maximum688 actors:100 Supply,12 workers and60
structures each, with64 returning aircraft and336 scouts repeatedly rerouting.
The natural authorized view shows172–257 actors. It is synthetic performance
geometry, not a balanced shipping map or proof that688 actors were simultaneously
visible. Commands, initial/final hashes and metadata are generated by
`TestExportBrowserMaximumLoad`; the real browser worker must match them exactly.

## Baseline and graphics backend

`client/tests/render/load-browser.mjs` executes two consecutive600-tick segments,
using four-tick batches and5Hz snapshots. RPC measurements include Go simulation,
view conversion, worker messaging and main-thread frame handling. They are not
isolated per-tick timings. Both segments preserve final hash, save restoration
and disposal to zero canvases/resident sprite pages. They are30seconds of
simulation each, not long-match memory acceptance. Art remains incomplete.

The initial headless run uses SwiftShader software rasterization and reaches
13.27–14.20ticks/second. The [independent GPU/profile diagnosis](../work/evidence/browser-render-profile/diagnosis.md)
confirms that its software GPU consumes roughly seven CPU cores. The same frozen
old adapter on headed Chromium/ANGLE Metal AppleM4 reaches600ticks in30seconds,
with RAF p50/p95 of16.7/18.4ms; a no-draw control is similar. Main-thread JS is
not the cause of the headless50ms frame interval. These are measured host-specific
results, not Intel target, actual Safari or completed-asset certification.

The resource-free fixture also exposed a valid Go map with `fields:null`.
Renderer asset preparation now treats that empty resource list safely. The first
failed run is preserved under `work/evidence/browser-load/attempt-01`.

## Derived-data and adapter improvement

Profiling the exact600-tick native adapter path found avoidable allocation:
full PlayerView construction for every local human every tick just to retain
feedback, plus discarded fog grids and source-tile lists. The implementation now:

- Uses one shared `PlayerFeedback` authorization filter for owner/team/visible
  events, impact identity redaction and private command receipts. The browser
  retains this narrow output between display frames.
- Reuses only derived visibility buffers and per-source tile storage. Held
  player snapshots remain independent copies. Authoritative state and save
  serialization are unchanged.

The same native adapter benchmark decreases timed allocation from1,879,107,560
to685,915,368bytes (about63.5%) across600ticks. Allocation counts decrease from
12,758,309 to11,053,111. Runtime7.88s→6.04s is recorded, but those single samples
on a shared workstation are not a latency acceptance gate. Both runs reach
`8f1bc930891145054177f3086d2e268da1180935dc782a922b101e53b4adf32c`.

Authorization/redaction and held-view/cold-restore tests pass. The complete
short simulation/adapter suites, focused race checks, both TypeScript checks,
189 runtime tests and actual Chromium/Firefox/WebKit native/WASM parity,
persistence, offline, sync and two-browser multiplayer checks also pass after
the change. A rendered comparison with the updated adapter and complete art,
long sessions, real Safari and reference laptops remains required.

## Reproduction

From the repository root, export the optional fixture before running the browser
runner. Neither command modifies production gameplay content.

```sh
FRONTLINE_BROWSER_LOAD_DIR="$PWD/work/evidence/browser-load" \
  go test ./pkg/sim -run '^TestExportBrowserMaximumLoad$' -count=1 -v
node client/tests/render/load-browser.mjs
```

The browser runner currently reads the isolated `build-terminal/product` runtime
and asset copy. Record its exact hashes and chosen graphics backend before any
comparison; it intentionally does not silently substitute a newer live pack.
The independent headed profiler records the precise hardware procedure.
