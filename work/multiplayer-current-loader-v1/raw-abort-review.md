production change or error waiver. The newly prepared current-loader matrix has

## Feasible bounded successor

Yes: a separate **test-only** successor can attach the existing native reader
observer before navigation to each selected page, without changing frozen product
bytes, fetch arguments, delivered chunks, the host or Go. `captureAssetGeneration`
binds `globalThis.fetch` during boot, so attaching after the game starts or after
an abort cannot recover original consumption. The frozen v3 core normally uses
one default `response.body.getReader()` stream, hashes verified bytes itself and
then parses/decodes them. That is compatible with the prior original-reader
observer. No response clone, tee, second download, body reread or fetch retry is
needed.

Expected bytes must come from the **preverified build03 manifest at capture**,
including its exact index/pack identity, before any request starts. Never choose
an expected hash by matching whichever body arrived. Each proof still needs the
same native request ID, page target, default execution context, frame/document,
observer script, full URL/method and unique per-document ordinal; serial/no-overlap
and one-to-one counts remain mandatory. Redirects, worker-generated responses,
unknown realms, ambiguity, missing EOF, hash mismatch and observer overflow stay
unproved. A CacheStorage read or a subsequent Blob URL decode is not a new native
HTTP request and must not be assigned an earlier network ID.

Retain separate results:

- `rawDiagnosticStatus` uses every original CDP/PW failure, console/page/HTTP
  error and collector fault. An unexpected abort still fails it.
- `bodyProofs` attaches original EOF, exact byte count/SHA and actual cancellation
  observations only to uniquely identified same-run requests.
- `functionalStatus` and native replay proof stay independent. Body equality
  proves neither image/audio decoding nor a committed multiplayer result.

The present tiny diagnostic's1MiB/body and32MiB cumulative caps are **too small**
for this full product. Build03 has4,692 `/art/` files totaling553,387,062 encoded
bytes; its largest is `/art/ui/keyart/main_menu.png` at2,521,570 bytes. A proposed
first current-loader diagnostic should be a separately coordinated **one-page
readiness + bounded ordinary paid opening**, not instrumentation added silently
to the locked3H1AI matrix. Suggested hard caps are8MiB/body,768MiB cumulative,
16active incremental hashes (9,728 bytes of hash arrays),16,384 records and a
separately bounded CDP ledger. No response chunks are retained. Caps are coverage
limits, not a guarantee: repeated reloads can exhaust them, which makes affected
evidence incomplete. A full three-page match could hash hundreds of MiB per
page and change CPU scheduling; it needs explicit scheduling and cannot provide
uninstrumented performance or deadline-cause evidence.

Do not reuse the old all-Fetch-equals-identified assertion as a claim that native
JSON or browser Image/SVG bodies are observed. Instead list each consumer class
and every unproved request, without relaxing the strict raw failure gate. Keep
the supported original-reader proofs and their negative controls. Any eventual
posthoc selection must be labeled and use the descriptor authorized at that
request's phase, as the initial-A analysis did.

The current prepared matrix and its receipt remain unchanged by this review.
A proposed diagnostic derivative should retain that baseline and add only pinned
test instrumentation/negative proofs after root authorizes it.
